Ligne « Graphes » — complétion des livrables en phase A

0.6.0-dev : sources, tests, benchmarks et diagnostics préparés, non exécutés. La ligne utilisateur « variantes AMD/COLAMD, partitionnement multilevel et appariement pondéré » est écrite pour les fonctionnalités pertinentes de l'amont Rust 8d82bb6bf1df133aa90525aa9f478ebe41514f9b. Ce constat porte sur les livrables ; ni le chargement, ni la correction, ni les performances ne sont attestés. Aucun code Julia/Rust du projet, test, benchmark, compilateur, précompilation, autotuning ou générateur LLVM n'a été exécuté pendant ce lot.

Le premier lot graphes reste la description des bases. Ce complément ferme son audit pour cette ligne et remplace ses mentions « raffinement seulement glouton », « variantes encore à auditer » et « adaptateur Rust absent ». La mission globale OxiBLAS reste partielle.

Contrats et limites restant explicites

Les noms AMD et COLAMD de l'amont ne désignent pas les algorithmes SuiteSparse correspondants. Le port ne remplace pas les implémentations exactes déjà écrites par des alias trompeurs. Les variantes pertinentes de l'amont sont rapprochées ci-dessus ; développer le vrai quotient-graph AMD/SuiteSparse COLAMD avec leurs heuristiques optimisées constitue un travail supplémentaire, pas une fonction Rust pertinente encore cachée derrière ces noms. Aucune performance équivalente à SuiteSparse/METIS n'est annoncée.

Les algorithmes d'ordonnancement/graphes restent séquentiels. Les appels sont indépendants et ne partagent pas de workspace mutable ; les tests préparent GC et appels simultanés. Les campagnes 1/2/4/8 threads servent aussi à contrôler l'environnement et les appels concurrents ; aucun speedup intrinsèque de ces algorithmes séquentiels n'est revendiqué. La recherche par degrés exacts et le remplissage symbolique peuvent être coûteux en temps/mémoire. La construction d'un grand graphe symbolique n'est pas un algorithme streaming/distribué. Aucune API graphes distribués n'est présente dans les modules audités.

L'appariement carré de graphe et l'incidence rectangulaire ont des sens distincts. Pour un graphe, saturatedsmallerside indique la saturation de la plus petite couleur et coversallvertices indique si tous les sommets sont couverts. Cela évite de reproduire le champ amont isperfect, dont l'implémentation teste la saturation de la plus petite couleur malgré une documentation « tous sommets ». Les objectifs et limites de normalisation Float64 de l'appariement pondéré sont inchangés et décrits dans LOTGRAPHES_CREUX.md ; pas de certificat exact des poids.

Le raffinement :greedy reste le défaut des APIs multiniveaux, préservant leur politique antérieure. :fm est optionnel ; refine_partition utilise :fm par défaut. Chaque passe verrouille un sommet après son déplacement, actualise les gains voisins et conserve seulement le meilleur préfixe selon violation d'équilibre puis coupe. Une exploration temporaire peut dépasser l'intervalle de charge d'un sommet maximal ; les tailles minimales des deux parties restent imposées. La coupe et la charge sont recomputées après rollback, avec retour à l'état initial si l'amélioration n'est pas retrouvée en précision de travail. Ce n'est ni une recherche globale ni une implémentation de toutes les variantes KL/FM. Les tas utilisent des versions paresseuses ; la recherche d'un déplacement admissible peut rescanner des candidats bloqués par les poids, donc le pire cas n'est pas annoncé linéaire. Le scratch des candidats bloqués est réutilisé dans la passe.

Les séparateurs par niveaux n'ont pas d'arêtes entre leurs deux côtés. Si le sous-graphe est déconnecté, ses composants sont séparés sans supprimer de sommet. Les feuilles utilisent un minimum-degree local exact. Les séparateurs multiniveaux restent des couvertures gloutonnes, pas nécessairement minimales. maxdepth borne la récursion ; les feuilles éventuellement grandes restent traitées explicitement. Les poids indivisibles, tolérances impossibles ou heuristiques peuvent empêcher l'équilibre : les résultats exposent le critère obtenu sans prétendre le garantir. Les poids d'arêtes qui deviennent nuls par normalisation sont désormais rejetés au lieu d'être silencieusement perdus ; la même politique existait pour les sommets.

Les conventions de mesures sont désormais explicites : bandwidthprofile garde sa largeur matricielle lower+upper+1 et son profil inférieur ; graphbandwidthprofile fournit max(lower,upper), somme des portées de lignes et moyenne, comme le module graph Rust. orderingmetrics expose les deux familles. Son fillratio = factornnz / patternnnz, où patternnnz inclut la diagonale et le triangle du motif symétrisé. L'amont fillinratio soustrait le nnz stocké de l'entrée avant division : cette convention dépend du stockage et peut différer. Elle n'est pas présentée comme le même chiffre. Le profil du module ordering Rust ajoute aussi 1 par ligne occupée ; son code soustrait des indices non signés sans borner les lignes strictement supérieures. Le profil inférieur Julia garde la diagonale implicite et évite cette soustraction non définie pour certains motifs. Il n'est donc pas annoncé bit-à-bit identique au profil ordering Rust. Les zéros numériques sont ignorés par le port ; l'amont compte parfois des zéros explicitement stockés comme arcs.

Tests et campagnes préparés

Les six fichiers du lanceur ciblé couvrent les API de cette ligne, avec références exhaustives/denses et invariants indépendants : quatre types natifs, vides/rectangles/isolés, triangles uniques, signes/phases/poids logarithmiques, appels simultanés, GC, permutations, remplissage, coupes/charges/séparateurs, BFS/composantes, rollback des passes FM, échelles et options invalides. Les longs chemins HK et postordres ont 4096 sommets. Les erreurs et cas d'équilibre impossible sont préparés. Tous ces tests sont intégrés, non exécutés.

Le benchmark natif mesure chaque famille de la ligne avec gardes avant timing, premier appel/compilation, min/médiane chauds, allocations et stockage conservé. Le Rust préparé mesure en processus séparé un sous-ensemble Float64 pertinent au même checkout : matching, degrés/colonnes/dissection, mesures et partitionnement. Les fichiers cases-fnv64.csv et la colonne csr_fnv64 Rust utilisent exactement le même encodage des CSR (m/n, indices zéro, bits Float64 little-endian). Le script de comparaison refuse une entrée Rust absente du manifeste Julia. FNV sert à la correspondance des cas, pas à une garantie cryptographique ; les sources, matrices natives, logs et résultats disposent aussi d'empreintes SHA-256. Les heuristiques peuvent produire des permutations/coupes différentes : les qualités sont rapportées, jamais supposées identiques au Rust. Les premiers appels Julia incluent la compilation, les appels Rust compilés ne l'incluent pas. Les benchmarks d'ordonnancement Rust/natif partagent des entrées, sans prétendre avoir le même algorithme optimisé ou le même temps. Pas de référence BLAS/LAPACK pour ces algorithmes combinatoires, et pas de provider SuiteSparse/METIS ajouté.

Les phases sont séparées et ne s'enchaînent pas automatiquement. Les dossiers doivent être neufs ; un échec conserve les logs complets, le code de retour, les timestamps et hashes puis arrête la phase. Rust est construit –offline, sans téléchargement implicite ; une dépendance absente produira un échec explicite. Le coût exact reste inconnu ; les 7 échantillons / 0,15 s cible par cas ne bornent pas une compilation ou un appel individuel. La reprise automatique reste du ressort du lanceur global à terminer ; les résultats partiels restent intacts.

Ce n'est pas une demande anticipée d'exécution. Selon le protocole, la première autorisation sera demandée lorsque les livrables globaux seront prêts. Les archives/mesures v0.5 et manifests historiques ne sont pas remplacés par ce lot.
